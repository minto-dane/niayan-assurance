# ADR-0056 検査済み世代とcatalogの単一確定

状態: proposed-for-review。独立承認と製品受入は未実施。

## 背景

ADR-0055の分割組立ては非公開rootを完成させる。検査終了時に予約を解放すると、
公開前に別の協調writerが内容を変更できる。また、ファイル実行器のApplyで書いた
ポインタを現行世代として読むと、Commit前に新catalogとrootを公開してしまう。

## 決定

`Pkg_Generation_Stage.Verify_And_Hold`は全物理検査後もgeneration.lockとroot.lockを
保持する。CASだけを閉じ、公開実行器が同じCASを取得できるようにする。
呼出し側は必ずCloseし、保有中のcontextを上書きしない。

`Pkg_Generation_Descriptor`はroot identity、stage identity、マニフェストとcatalogの
digest、公開世代番号、直前descriptorのdigestを192 bytesの正規形式に束縛する。
公開プランは固定の`generation.next`一件だけを対象とする既存ファイルプランである。
このファイルは未確定の作業領域で、現行世代を示す権威ではない。

`Pkg_Generation_Publisher`は全gateを必須とする`Pkg_Managed_Engine`をgeneric引数に取る。
新規の別WALを作らず、既存root.stateのGeneration/Accepted_Plan/Package_Setを使う。
Accepted_Planが参照するCASのdescriptorだけが論理上の現行root/catalogを選ぶ。
Active_Transactionが残る間はRead_CurrentがIndeterminateを返し、descriptorは空にする。
確定記録が最後まで揃った時だけ、同じdescriptorからrootとcatalogを返す。
これは論理世代の確定であり、実際のmountやboot切替ではない。

排他取得はpublication.lock → root.lock → CASの順で始める。対象の整合性を検査後、
publication.lockを保持してroot.lock/CASを解放し、stageの全体検査と予約を取得する。
その後ファイル実行器がroot.lock/CASを再取得し、観測済みroot.stateと照合する。
各実行境界でstage予約の束縛と全Managed.Guardを再検査する。
協調する公開・削除・将来のGCは同じpublication.lockとstage予約に従う必要がある。
ロック取得失敗は待ち続けずに失敗する。

新しい要求の前には直前のaccepted planとcatalog・descriptor・終端journalを検査する。
進行中の要求の再開ではその要求自身のjournalを検査する。commit前、root.state更新後、
Committed追記後、応答喪失は既存replayを使い、別の公開世代を追加しない。
記録済みhealth receiptの差替え、restore、journal repairはこの公開器では許可しない。
欠落したlock/state/journalを空として再作成しない。

## 代替案

稼働世代をsymlinkやgeneration.nextだけから読む方式、rootとcatalogを別々に確定する
方式、第二のPython特権writerや別の公開journalは採用しない。
全Managed gateを公開器内へ複製する方法も、契約を二重管理するため採用しない。

## 影響

新しいruntime SDKは非特権でUID 0を拒否し、公開コマンドや既存workerを変更しない。
bootstrap認可とstage認可も必須で、組立てへの認可を公開認可へ転用しない。
stageの変更は非公開時だけ許す。accepted stageの再照合は読取専用の認可として区別する。
Read_Currentはメタデータの観測で、実行許可や現在の物理root/bootの健全性を保証しない。

予約に従わない同一所有者や特権による変更はモデル外である。本番では外部writerの
排除、権限分離、起動前の再検査と独立trust floorを別途接続する必要がある。
既存のSPARK数理層と固定vendorは変更しない。新runtimeは形式証明済みではない。

## 検証と残る条件

隔離試験は二つの人工世代、実CAS/WAL、全Managed guard、試験専用二役署名を使用する。
実DEBの効果・物理barrier・独立trust floorの証明は提供しない。
認可取消、期限切れbarrier、破損署名、構成sequence不足、native coverage不足、
trust floor不足、native照合拒否、最終再観測拒否、途中適用・確定と再開を検査する。
不正descriptor、欠落journal/lock、作業ファイルとaccepted記録の混同も検査する。

実際のmount/boot切替、利用中資源の停止・復帰、全DEB意味、catalog/holds、特権metadata、
容量予約、fsync故障・実電源断、rescue、本番認可と新ISOの受入は未完である。
人工の永続prefixによる復旧試験を実電源断の証跡として引用しない。
