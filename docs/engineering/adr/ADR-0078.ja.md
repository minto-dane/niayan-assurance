# ADR-0078 認証した供給原本のnative CAS照合

状態: proposed-for-review。本番observer/key配備と公開計画全体への接続は未認定。

## 背景

PythonのTUF/OpenPGP認証とnative catalogは同じ元DEB/controlを扱うが、観測JSONの成功flagを
別プロセスの認可として信用できない。既存の取得grantは別の供給形式・trust状態を持つ。

## 決定

[供給記録](../../../../distribution/native/archive-receipt.ja.md)の固定NIASUP01を使用する。
既存MC_AuthenticのEd25519/domain framingを使い、TUF認証したpolicy・原本・期限へ署名する。
発行関数は実際のTUF/OpenPGP認証を必須とし、任意の観測recordを受け取らない。
署名providerと独立公開鍵を必須にし、既定鍵や新しい公開CLI・第二のtrust cacheは作らない。
nativeは独立scope/key/floor/timeと全参照CAS objectを照合し、元DEBのcontrolを再観測する。

## 代替案

自己申告JSON、供給形式の異なるgrantの流用、既存witness factの意味変更、暗号方式の独自実装を
採用しない。上流TUF/OpenPGP検証をnativeへ再実装する方針も採用しない。

## 影響

署名するobserverと鍵・適用範囲の保護が明示的な信頼境界となる。署名だけで観測の真実性は証明できない。
発行後の失効や最新remote policy確認、全公開計画の変更集合との一致、保持閉包・世代への束縛は
別の必須検査である。一つの原本の検証を全計画の成功や実行許可として使用しない。

## 検証と残る条件

実TUF/OpenPGP発行とnative原本照合を一つの標準検査に接続する。署名/domain/全byte/全参照、
独立authority/time、正しく署名された不正controlも拒否する。発行者秘密鍵は試験一時領域だけで使う。
新しいruntimeはSPARK対象外。既存数学的入力の集合は確認し、不変なら証明を重複実行しない。
本番配備、全計画の供給網羅性・保持・同意・phase/効果/所有権・実root/bootは引き続き未完。
