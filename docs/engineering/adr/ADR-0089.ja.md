# ADR-0089: 明示的なnative storage bootstrap

## 背景

root準備サービスの配布物は存在するが、従来のVM受入では人工fixture driverのCAS作成後に
一時停止してbankを用意していた。この試験調整を製品installerの実装とすることはできない。

## 決定

既存MC_StoreのInitialize/Openを内部pkg_store_bootstrapから呼ぶ。共有API・永続形式は変更しない。
UID0を拒否し、初期化と構造checkだけをversion付き機械応答で公開する。内部配置のみとする。
root側のstorage_bootstrap.pyは固定既定pathとv2 policy、専用accountと保護された実ELF、
停止済みunitを必須とする。排他的・永続intent、専用directory、非rootの実CAS初期化、
保護mount、既存bank provisionerの順に進め、最後にだけ別の完了記録を作る。

既存・途中状態に対する自動修復や上書きを行わない。socket有効化、供給/認可policyの
自己生成や実rootの公開はこの処理に含めない。失敗後も記録と部分状態を保持する。
root準備daemonは独立したFD境界なのでpkgcoreを必須実行依存にはせず、明示bootstrapは
新しい内部ELFの配備を必須検査する。installerは両成果物の組合せを管理する。

## 代替案

試験driverの製品化、手書きstore.lock、サービス起動時の自動Initialize、
不完全状態の削除後再試行、自己報告hashによる認可は採用しない。

## 影響

内部appの成果物在庫が一つ増える。通常起動の条件と共有vendorは不変であり、
初期化記録の追加によって途中配備を明示的に扱う必要がある。

## 検証と残る条件

実ELFの新規/既存/欠損/予約競合/非private/symlink拒否を一時領域で確認する。
使い捨てDebian 13 VMでは配布済み工具でstorageを初期化してから既存CASを開き、
実unitからrootを準備する。再起動・欠損拒否を確認し、sourceと成果物hashを証跡へ束縛する。
全suite・不変の形式証明・カオスcampaignは繰り返さない。

本番認可/供給provider、導入先選択/保守環境の全installer、容量予約、物理再検証/GC、
全DEB効果、起動切替、完全置換ISO、全言語翻訳は未完。独立設計レビューは未承認。
