# ADR-0092: 独立供給observerの実サービス配布

## 背景

credential署名providerと現在site供給policyの読取は実装済みだが、保護設定・既存cache・
HTTPS・原本FDと実core clientを結ぶ配布物がなかった。任意署名daemonや別の導入済みDBは不要である。

## 決定

専用nia-supply UIDのsocket起動サービスが一件ずつ原本FDを受け、私有copyから既存TUF/OpenPGP認証と
credential署名を行う。保護設定のscope/key/floor、core peer UIDと現在時刻を使い、前後で設定を確認する。
receipt/policyをsealed read-only FDで返し、clientは実sender credentialsと独立公開鍵を検査する。
既存共通TUF checkpointだけを使い、通常serviceは状態を自動作成/chownしない。
明示provisioningと排他的intent/完了を分離し、初期化成功を実行許可にしない。
独立Debian packageは必要な正本moduleだけを輸出し、上流依存を改変せず停止状態で導入する。

## 代替案

任意message署名、callerのURL/keyによるauthority作成、失われたcacheの自動bootstrap、rootでの
原本解析、packet内への大きなpolicy詰込みは採用しない。StateDirectoryによる所有者調整は明示初期化だけに限定する。

## 影響

独立した内部packageと二service/一socketが増える。公開管理コマンドと共有API/vendor、永続receipt形式は不変。
秘密seedの配備元保護、独立site policy/floorとの鍵更新、非rollback storageと正しい時刻はinstaller/運用の責務である。
serviceの資源上限で大きな入力が拒否され得る。拒否前にTUF floorが進んだ可能性を保持する。

## 検証と残る条件

関連単体試験、独立directoryのDEB再現性、実systemd配布物とHTTPS、一時credential、native CASをVMで確認する。
通常の連続要求、別peer/原本/設定/鍵/TLSとstate保護・lock欠損を扱う。
VM fixtureと配布工具の成功は、全production installer、controller/全managed認可、全DEB効果や実bootの完成ではない。
