# ADR-0095: 元DEBのconffilesと三者比較

## 背景

全managed認可にはConfiguration/Side_Effectsの完全な解釈が必要だが、元conffilesのnative解釈と
利用者変更を保持する更新判断が未実装だった。単純なpayload上書きは編集・削除された設定を壊し得る。

## 決定

元DEBのcontrolと対応payloadから宣言を再観測し、完全なpath bytes/属性と原本hashを保持する。
旧vendor・現在・新vendorの内容を区別し、両者変更では利用者選択を要求する。
通常削除、purge、remove-on-upgradeと退避義務を区別し、次回比較に必要なvendor baselineを保持する。
判断と実行認可を分離し、未解決判断は実行しない。欠落と読取不能を同一視しない。

## 代替案

常時新vendorで上書き、利用者削除を欠損修復する方法、無条件text merge、上流MD5を認証に使う方法は採用しない。
既存の共有ASCII文字列型をraw filenameへ使わず、native payloadと同じ有界byte文字列型を使う。

## 影響

非root内部の宣言読取と内容判断を追加する。共有API/vendorと数学的入力、永続世代形式は不変。
ASCII型を使っていた供給plannerのpathもbyte保持へ修正し、下位transportでUTF-8を検査する。
全属性/所有権・リンク・生成script・退避名/保持履歴・実root組立てと公開への接続は引き続き必要である。

## 検証と残る条件

原本の通常/不在/空/flag/byte名/リンクと不正宣言、独立したdpkg 1.22.22の隔離rootで
実更新・通常削除・purge・確認・退避・baselineを比較する。scriptは持たずhost rootへは書かない。
供給plannerのpath変更もcompileと実service経路で確認する。
この受入を全設定効果、全managed認可、全DEB対応や稼働OS更新の完成にはしない。
