# ADR-0103: 原本をまたぐrootの親先行順と旧記録の保持

## 背景

従来のroot生成はdirectoryを元DEB hash/元tar位置順に並べる。
親子の採用元が異なる場合や元tarが逆順の場合、子がroot/親より先になる。
実展開workerはroot entry先頭・親の非自動生成を要求するため、生成側との契約が一致していない。
既存manifestの検証は再生成した全byteの一致に依存するので、順序だけを無版変更してはならない。

## 決定

BuildはNIAROOT2を出力し、directoryをcanonical raw path順とする。
rootを最初に、親を全子より先に出す。その他は既存の元DEB/元tar位置順とhardlink依存順を保つ。
元header/拡張/body/paddingを改変せず、最終順でもroot/親先行を検査する。

Verify/Verify_TargetはNIAROOT1を従来の順序で再検証し、既存recordのhashとbyteを保持する。
実展開前にも使うVerify_Ownershipは、旧形式の順序がroot/親先行を満たさない場合にUnsupportedを返す。
適切な旧順は受理する。再構築が必要な旧recordは、新しいplanと通常の認可を必要とする。

## 代替案

workerの親自動生成、元DEBの書換え、NIAROOT1の意味を無版で変更する方法は採用しない。
過去recordを暗黙に新hashへ更新する方法や、過去の読戻し成功を実展開許可へ昇格する方法も採用しない。

## 影響

内部root manifestのmagicだけを版更新し、既存152 byte headerとclaim選択の配置を維持する。
NIAGEN05の既存root hash参照と保持/世代公開APIは変更しない。rootの設定配置も既存Verify_Ownershipを通る。
共有vendor、数学的入力、公開コマンド、workerの隔離と親非自動生成を維持する。

## 検証と残る条件

二つの逆順directory原本からroot/親/子の採用元を8通り組み替え、独立Pythonで原本spanと順序を検査する。
通常の世代stage、設定配置、root archiveを使う公開variantを変更境界として検証する。
使い捨てVMで生成tarの実展開・属性・内容・負時刻・hardlink chainを確認する。
旧形式のbyte一致と適切な旧順の受理、不適切な旧順の物理準備拒否も検査する。
全root設定の直列化、全属性/inode効果、production認可、保持/復旧・実boot、完全置換ISOは未完である。
