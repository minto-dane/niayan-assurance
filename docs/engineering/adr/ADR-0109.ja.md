# ADR-0109: 設定済み世代の公開と受理済み記録の復旧

## 背景

NIAGEN06を準備できても、公開engineへの接続が必要である。公開前に照合した設定元は、受理後に
変更されることがある。受理済みの決定を修復するために古い設定元へ戻すことはできない。
一方、active transactionが存在するだけで現在照合を省くと、未受理の古い設定を公開してしまう。

## 決定

Pkg_Generation_Publisherへ既定拒否のObserve_Configuration_Sourceを追加する。v6の新規公開と
未受理の途中再開は、stage検査時と公開engineが実CAS予約を取得した後の両方で通常Check_Currentを
実行する。providerは期待世代/root/transaction/contextと選択・失効・phaseを独立に認可し、借用FDと
source排他を操作全体にわたって維持する。stage検査後にsourceが変われば公開stateを更新しない。

受理済みの場合だけ、独立した限定型Retained_Generationから実stageを検査する。通常の
Verified_Generationへ変換できず、新規公開・未受理再開・展開・bootの許可には使えない。
inspect-retained / inspect-retained-batch / inspected-retainedの段階別認可、物理shapeと全byte、
全batch journal/receipt、世代とbatchのpin、保存設定閉包の照合は維持する。

実root.stateが要求planのtarget generation、accepted plan、catalogと完全に一致することを
公開engineの予約下でも再確認する。完全な同一journalがCommit_PendingまたはForward_Finalである
ことを要求する。この経路のguardはfinish-terminalだけを許可し、既存engineが全after-imageと
元health receiptを照合して、必要ならCommitted記録を追加しactive欄を解消する。
sourceの古いproposalは復活させない。通常の供給鍵/floor/age、構成承認、停止条件、resolutionと
独立認可はこの復旧でも現在の条件で照合する。呼出し側Booleanによる公開検査の省略は提供しない。

## 代替案

v6を単純に許可形式へ追加して保存recordだけを確認する方法、active記録だけでsource確認を
省く方法、受理後にも古いsource属性を要求する方法、通常のstage証拠と保存証拠を同じ公開型へ
混在させる方法は採用しない。下位engineのafter-image/journal/receipt判定は変更しない。

## 影響

v4/v5公開と旧generic呼出しは維持する。v6の初回公開・途中再開には新providerが必要となる。
受理済み記録の修復には元source FDを必要としないが、完全な保存世代と現在の復旧認可が必要である。
欠落した記録、stageのtar、journalやpinを推測・再生成しない。検査失敗では受理済みstateを維持する。

対象は保持archiveを選択する論理的公開SDKである。抽出済みfilesystemの検証、実root/boot切替、
boot後のmount/inode identity移行と、その物理的適用途中の復旧は別の未完条件である。
本番source排他・認証provider、全DEB効果、GC、完全置換ISO、全言語翻訳も未完である。

## 検証と残る条件

実conffile DEBを使い、local維持とvendor退避を含むv6を格納・公開する。既定provider拒否、
実engine予約でのsource拒否、未受理再開での拒否、stage検査後のsource変更、受理後source変更、
元FDを閉じたterminal retry、元health receipt、二つの受理済みcommit窓を検査する。
新プロセスの受理済み再開と6種の必須証拠欠落を検査し、独立wire/tar読取で実stateと選択済みbyteを
照合する。標準CIへ同じwrapperを登録する。これは人工認可を用いた限定試験であり、本番認証の受入ではない。
