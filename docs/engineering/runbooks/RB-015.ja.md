# RB-015 コア・カタログ・履歴の破損

1. 変更対象を隔離し、未確定要求と関係するwriterの状態を保全する。無関係の正常サービスを一律に停止しない。
2. core/kernelが疑わしい場合は、署名済み独立rescueと外部trustを使う。壊れた管理器が作る新しい鍵や空DBを採用しない。
3. 正確な外部anchor、現在の失効・世代下限、資格済み署名者を取得する。最も新しく見えるlocal timestampだけで選ばない。
4. read-only inspect/verifyを行う。元ディスク・破損chunk・監査記録を保全する。scrubやDB修復の前にも証拠を保存する。
5. 原本を組み合わせ、新しいcandidateへ再構成する。古いcandidateを上書きしない。全コピー欠落、証拠保存失敗、容量不足は成功扱いしない。
6. native catalog/WAL/receiver replay-window/信頼floorの完全性と対応を検査する。復旧後にpending外部効果を再照合する。
7. 認可されたexecutorが元のwriterを確実に停止し、別の回復点を残したうえで公開する。現行SDKと現場の接続が完成するまで手動承認の受け入れ工程を省略しない。
8. サービスと業務データの意味検査・観測を通して復帰を承認する。履歴欠落を正常空状態として扱わない。回復不能時はread-only salvageの範囲と失われた事実を報告する。
