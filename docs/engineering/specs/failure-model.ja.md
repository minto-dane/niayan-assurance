# 設計仕様 E-FAULT-1: 故障モデルと安全停止

## 想定する故障

プロセス停止、任意のwrite/fsync/rename間の電源断、復旧中の再停止、短い書き込み、ENOSPC、I/Oエラー、
部分末尾、完全レコード破損、CAS欠損、結果応答の喪失、古い観測、時計/bootの変更、ネットワーク分断、
同じサービスの重複制御、誤ったクラスタ接続、証明書の失効、復元後の古いtokenを区別します。
各故障の対応は`fault-cases.json`と運用手順で追跡します。すべてが実機試験済みという意味ではありません。

## 明示する前提

ローカルの対象FSが規定した永続化を守ること、所有者が管理器を迂回して並行変更しないこと、
外部資源側がfencing/書込み所有権を実際に強制すること、回復用データが少なくとも独立した保存領域に残ることを前提とします。
カーネル侵害、悪意ある同権限root、ストレージがflush完了を偽る故障、すべての鍵と全バックアップの同時喪失は、本コードだけでは回復保証できません。
対応しないNFS等を、openat2が成功したという理由だけで適格な永続領域にしてはいけません。

## 安全性と活性

安全性: 不明な状態で新しい破壊的操作を行わない、二重書込みを許さない、確定済みの判断を別のものへ変えない。
活性: 前提が回復し、必要な認可・隔離・データが揃えば、定義された再開経路がある。
停止予算を解放しないために保守が止まることはあり得ます。活性のためにfencingを偽ってはいけません。
監査サーバーや管理リポジトリの不通だけで、正常な既存業務を停止する必要はありません。

## 障害領域

プロセス、ノード、ストレージ、電源、ネットワーク、サイトを別々に定義します。
同じホスト上の3VMを独立した3障害領域とは数えません。
計画停止中の追加故障を許すかは容量・quorum・データ複製の契約に含めます。
RTOとRPOはサイトの契約値と測定結果を必要とし、この配布物の定数やマーケティング用の値ではありません。

## 復旧の優先順位

証拠保全と新規変更の抑止 → 書き込み所有権の確認 → 正しい媒体/鍵/世代の確認 → 限定した回復 → 実状態・業務状態の確認 → 段階的な復帰。
破損状態を初期化して見えなくすること、予算を削除すること、ログを消して成功扱いにすることは回復ではありません。
