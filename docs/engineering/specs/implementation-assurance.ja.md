# 実装言語と影響に応じた必須の検証基準

状態: 2026-09-12の利用者指示に基づく規範。既存実装の適合宣言ではない。
本番完成の条件に追加し、C以外への書換えによって要件を回避しない。

## 基準と適用範囲

NASA NPR 7150.2DとNASA-STD-8739.8を、要求追跡、設計、レビュー、検証、変更管理、
独立した保証活動の参照基準とする。Cの具体的制約には公開されたJPLのPower of Tenを用いる。
これはNiaOSの検証方針であり、NASA適合、飛行認証、DO-178C/DAL認定、MISRA完全適合を宣言するものではない。
商用規格の内容を推測して独自チェックへ置換しない。

最も厳しい対象は認証・認可・署名/供給、設定の採用、永続化・予約・取消、root/device/boot操作、
復旧・GC、特権サービスである。これらは、入力から外部効果と失敗後の状態まで追跡する。
UIの表示内容と同意対象の束縛、配布レシピ、CI、依存取得も信頼経路であり対象外にしない。
試験工具と証明harnessもレビュー対象である。第三者原本の改変や独自パッチは要求しないが、
対象版、信頼する性質、既知の限界、供給と対応ソースの根拠は別に保持する。

| 対象 | 必須の実装基準 | 必須の検証 |
|---|---|---|
| Ada/SPARKの判断・状態・形式 | 小さい型と範囲、Global/Depends/Pre/Post、ループ不変条件と終了根拠、所有権の明示 | 既存の厳格flow/proveに加え、実行時エラー不在と要求の機能的性質。認可・永続化・復旧は重要不変条件を証明する |
| Cと将来導入するC++等の低水準境界 | 単純な制御、再帰禁止、証明可能な反復上限、初期化後の動的確保禁止、小さい関数、最小スコープ、引数・戻り値検査、マクロ/ポインタ制約 | 実ソースに対する形式検証、メモリ/整数/状態の性質、警告ゼロと静的解析、ABIと実kernel境界試験。現在のC全体は未達 |
| SPARK対象外Ada・FFI | 外部効果を狭い境界へ隔離し、所有者・寿命・異常結果を契約化。Unchecked操作やSPARK_Mode Offは証明の代用にしない | 呼出側の前提と返却保証の整合、境界実装の検証、実ABI/資源/失敗試験。外部関数の契約だけを仮定して実装も証明済みとしない |
| 特権Python | 判断中核は検証可能なモデル/実装と対応付ける。型・状態・容量・期限を明示し、シェル評価、暗黙の権限昇格、例外の正常化を避ける | 厳格な型/静的解析、状態遷移の形式検証と実コードとの対応、実資格情報・取消・異常I/O・資源寿命の試験。モデルだけでPython全体の証明としない |
| その他のPython・UI | 型付き境界、厳密な入力schema、表示と機械識別子の分離、明示的な失敗 | 静的解析、要求に対応する試験、多言語/RTL/アクセシビリティ。同意や秘密情報を扱う部分には上段と同じ厳しさを適用 |
| シェル・Make・systemd・配布/CI設定 | 小さい再実行可能な処理、引用と終了値の扱い、最小権限、依存固定、secret非露出。重要な状態機械をシェルへ移さない | ShellCheck等の静的検査、構文/単位設定検査、隔離した失敗試験、再現ビルド、成果物と対応ソースの照合 |

## 形式検証の受入条件

証明対象のファイル/関数、要求・保証、ABI/整数幅、実行構成、ループ/資源上限、環境と外部関数の仮定、
工具/solver/設定、全入力hash、結果と未証明条件を保存する。証明harnessの仮定は要求から導出し、
正常入力だけへ絞って不正入力や異常結果を除外しない。恒偽の前提や到達不能化による空虚な成功を検査する。

CBMC等の有界モデル検査ではunwinding assertionを必須とする。上限の外を省略した成功、timeout、
unknown、工具不在、未評価、未モデル化の外部関数、検査の抑止を成功として数えない。
SPARKの検証深度オプションの値だけで、機能要件を証明したと主張しない。
TLA+等は並行性・故障・再実行・取消の状態機械に必要に応じて用いるが、Cのメモリ安全性や実コードへの対応を代替しない。

各新規変更の試験は変更境界に絞り、同一入力の成功試験を目的なく繰り返さない。
本番判定では要求ベース試験と負の試験、重要判断の分岐・条件網羅、独立レビュー、対象環境での統合・障害試験も必要とする。
静的ルールの正規表現検査、型検査、sanitizer、単体試験を形式証明と呼ばない。

## 移行と未完条件

既存Cの通常試験・ASan/UBSan成功はその範囲で保存するが、新しい必須条件への適合ではない。
追加中のroot handoffを含め、C実装の形式検証と規則適合は未完として管理する。
小さい純粋関数の証明が成功しても、同じファイルのOS操作、FFI、呼出側、外部ライブラリを一括認定しない。
既存SPARK結果も、証明対象外runtimeやPythonの特権動作を保証しない。

適合しない箇所を無言で例外登録しない。まず設計と実装を修正し、解消できない条件は本番未完として残す。
OS呼出しの成功を無条件に仮定するmodelや、失敗経路を除いたharnessで条件を緩めない。
3 GiB/swap0/CPU1/pids128の制限を維持し、証明は直列・有限時間で実行する。OOM/timeout時も上限を増やさない。
