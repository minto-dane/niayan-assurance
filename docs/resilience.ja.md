# 耐障害・復旧の設計と実装範囲

## 1. 責任の分離

パッケージの正本はpkgcoreの管理状態、プロセスの実状態はsystemd、クラスタの所有権は既存クラスタ管理器、共有予約はetcd、業務データはそのデータベースです。新しい管理器は全部の正本を複製しません。各観測をスコープ・世代・期限と結び付け、操作に必要な条件を検査します。

リカバリ決定のコードと、認証・永続化・FFIは分離しています。`src/`のSPARK契約を持つ判断器が計画を返し、`runtime/`のAda境界が再認可・永続化・観測・限定操作を行います。runtimeは`SPARK_Mode => Off`です。

## 2. 故障モデル

想定する入力には、古い/重複/未認証観測、通信分断、応答喪失、同時更新、中断、容量不足、部分最終レコード、依存サービス故障、再起動、ソフトウェアファイルのdriftが含まれます。

カーネル侵害、信頼した観測者の虚偽、rootによる全状態/高水位の一括置換、ディスクがfsyncに反して永続化しない故障、共通電源の喪失まで、管理器単独で排除したとは主張しません。別障害領域の監査・高水位、信頼可能な物理fencing、復元試験済みバックアップが必要です。

## 3. 単一ノードとクラスタ

単一ノードでは、systemdが所有するサービスを明示的なlocal policyのもとで復旧できます。etcdを使う共有予約SDKを組み込む必要はありませんが、workerの認可ゲートを飛ばす単独用裏口はありません。単一ノード用の正当な予約・所有権の証拠を発行するsite authorityは依然必要です。クラスタquorumを偽装するためのローカル署名は認めません。

クラスタ管理対象のサービスは、local workerが勝手にstart/restartしません。Pacemaker等を一つの所有者とし、maintenance/drain/reservationの調整を行います。systemdの自動再起動と新しい復旧器を競合させません。workerは他の自動再起動が設定されていれば操作を抑止し、自動で無効化もしません。

## 4. 自動復旧の条件

異常は複数の独立した時点の観測で確認します。観測間隔、最大鮮度、receiver boot、InvocationID、policy digest、resource/node/cluster scopeを検査します。正常復帰には複数サンプルと連続した安定時間を必要とし、プロセスのInvocationIDが変わったら時間窓をリセットします。

試行は効果より先にWALへ記録し、累積・連続・時間窓内の予算を消費します。指数待機は上限付きです。経過時間や再起動で累積予算を復元しません。時間窓の上限は待機で再判定できますが、緊急停止・侵害疑いはラッチし、勝手に解除しません。累積上限の更新やラッチ解除の完成済み管理APIはありません。ログ削除で回避することは禁止です。

一度のコマンドを「ちょうど一回、必ず反映」する保証はありません。送信後の曖昧な結果は`Outcome_Unknown`とし、blind replayしません。正当な停止/失敗観測による失敗確定か、新Invocationの安定した正常観測で解決します。

## 5. 実装レベルの分類

| 機能 | 実装レベル |
|---|---|
| 署名・方針・予算・WAL付きlocal service復旧 | 実操作コードあり。観測発行・要求dispatchはsite接続が必要 |
| healing WALの部分末尾保存/限定truncate | 実I/Oコードあり。独立した署名付きprefix/tail認可が必要 |
| etcdのrich reservation | 実mTLS/CAS SDK。qualified view/authorityはsite callback |
| rolloutのcanary/soak/失敗停止 | FSMとetcd永続化SDK。フリート全体の配布/実行daemonは未完成 |
| 書き込みfailover | 許可判断器。物理fencing driver・共有ストレージ権限切替ではない |
| RPM配布物のdrift検査 | 実ファイルscrub CLIあり |
| drift修復 | 制約付き計画生成SDK。既存の認可済みファイル実行器へ接続。自動署名/dispatch一式は未完成 |
| 回復点の選択/保持 | 判断器。バックアップ装置・CAS自動GC・起動更新ではない |

## 6. 統合で証明・試験する境界

署名は誰が情報を述べたかを確認しますが、物理的な事実の正しさの証明ではありません。service observerはhealth.binを署名する前に、依存、データ互換、所有権、業務応答を確認する必要があります。etcdのviewはwatch cacheだけで認可せず、qualified fresh snapshotとCASを使います。

systemd/etcdへ送った要求は、helperが死んでも相手側で続行する可能性があります。子プロセスへparent-death signalを設定しても、外部効果の取り消しにはなりません。I/O timeoutもカーネル内で停止した装置を必ず中断できるhard real-time保証ではありません。

## 7. 承認ゲート

既存バイナリ配布を再利用しますが、受け入れ集合と互換契約の保守は必要です。GNATprove、Ada単体試験、FS障害注入、クラスタ分断/fencing、データ復元、鍵更新/失効、負荷/長期試験を完了し、siteごとの根拠を記録するまで、本番認定フラグを立てません。
